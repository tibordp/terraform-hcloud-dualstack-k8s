# Upgrading from v2 (keeping the existing cluster CA)

In v3 the cluster PKI (the Kubernetes, front-proxy and etcd CAs, and the
service-account signing key) is generated by Terraform and held in state,
instead of being generated by `kubeadm init` on the first node. v3 also
replaces the v2 provisioning resources, so a v2-created state cannot be
applied with v3 directly.

An existing cluster can still be migrated in place, without rotating its CA,
by seeding the Terraform state with the PKI that kubeadm generated. The
`tls_*` resources do not support `terraform import`, so this is done with a
targeted apply followed by a state edit.

Throughout this guide the module is assumed to be named `module.cluster` —
substitute your own module name in all resource addresses.

## Prerequisites

* A healthy v2.x cluster with kubeadm-managed CAs (`/etc/kubernetes/pki/ca.key`
  exists on the control plane nodes; this is the kubeadm default).
* Kubernetes 1.29 or newer. The v3 admin credential uses the
  `kubeadm:cluster-admins` group; verify the binding exists:

  ```console
  $ kubectl get clusterrolebinding kubeadm:cluster-admins
  ```

* Terraform >= 1.9, `jq`, and SSH access to the nodes as `root`.
* Nobody else running applies against this state until you are done.

Back up everything first:

```bash
terraform state pull > v2-backup.tfstate
ssh root@<control-plane-0> 'ETCDCTL_API=3 etcdctl snapshot save /root/etcd-backup.db \
  --cacert /etc/kubernetes/pki/etcd/ca.crt \
  --cert /etc/kubernetes/pki/etcd/server.crt \
  --key /etc/kubernetes/pki/etcd/server.key'
```

## 1. Fetch the PKI roots from a control plane node

```bash
CP0=$(terraform output -json control_plane_nodes | jq -r '.[0].ipv4_address')
mkdir -p pki && chmod 0700 pki
for f in ca.crt ca.key front-proxy-ca.crt front-proxy-ca.key sa.key sa.pub; do
  scp "root@${CP0}:/etc/kubernetes/pki/${f}" "pki/${f}"
done
scp "root@${CP0}:/etc/kubernetes/pki/etcd/ca.crt" pki/etcd-ca.crt
scp "root@${CP0}:/etc/kubernetes/pki/etcd/ca.key" pki/etcd-ca.key
```

These are the cluster's root keys. Keep them out of version control and
delete the directory once the upgrade is verified.

## 2. Mark every existing node as provisioned

v3 guards `kubeadm init`/`kubeadm join` with a marker file instead of v2's
`$HOME/.kube/config` check. Without the marker, the v3 provisioners would
re-run kubeadm on your existing nodes (and fail preflight). Create it on
every control plane **and** worker node that Terraform manages:

```bash
terraform output -json control_plane_nodes | jq -r '.[].ipv4_address' | while read -r ip; do
  ssh "root@${ip}" 'touch /etc/kubernetes/.terraform-provisioned'
done
# repeat for each node of every worker pool module
```

Nodes that joined via the `join_user_data` cloud-init (e.g. cluster
autoscaler) are not managed by Terraform provisioners and need no marker.

## 3. Update the configuration

* Bump the module version to v3 in every place it is used (the cluster module
  and all worker pool modules).
* Remove the `kubeadm_host` variable if you set it (it no longer exists).
* The `join_command` output is gone; external consumers should switch to
  `join_user_data`, or `discovery_conf` + `worker_join_config`.
* Run `terraform init -upgrade` (v3 adds the `hashicorp/tls` provider).

If your cluster predates the kubeadm RSA-2048 default changing, you don't
need to set `ca_key_algorithm`/`ca_rsa_bits` — they only affect newly created
PKI and are ignored from here on (the PKI resources are write-once).

## 4. Create the PKI resources with throwaway values

Create just the PKI objects in state. The keys and certificates generated
here are placeholders and will be replaced in the next step — do **not** run
an untargeted apply until the swap is done.

```bash
terraform apply \
  -target='module.cluster.tls_private_key.ca' \
  -target='module.cluster.tls_self_signed_cert.ca' \
  -target='module.cluster.tls_private_key.sa'
```

Expect exactly 7 resources to be added and nothing else to change.

## 5. Swap in the real cluster PKI

Pull the state, replace the throwaway PEMs with the files fetched in step 1,
and push it back:

```bash
terraform state pull > v3-upgrade.tfstate

jq \
  --arg mod "module.cluster" \
  --rawfile kubernetes_crt pki/ca.crt \
  --rawfile kubernetes_key pki/ca.key \
  --rawfile front_proxy_crt pki/front-proxy-ca.crt \
  --rawfile front_proxy_key pki/front-proxy-ca.key \
  --rawfile etcd_crt pki/etcd-ca.crt \
  --rawfile etcd_key pki/etcd-ca.key \
  --rawfile sa_key pki/sa.key \
  --rawfile sa_pub pki/sa.pub \
  '
  def patch($type; $name; $key; $attrs):
    (.resources[]
      | select(.module == $mod and .type == $type and .name == $name)
      | .instances[]
      | select((.index_key // null) == $key)
      | .attributes
    ) += $attrs;

  patch("tls_private_key";      "ca"; "kubernetes";     {private_key_pem: $kubernetes_key})
  | patch("tls_self_signed_cert"; "ca"; "kubernetes";     {cert_pem: $kubernetes_crt, private_key_pem: $kubernetes_key})
  | patch("tls_private_key";      "ca"; "front-proxy-ca"; {private_key_pem: $front_proxy_key})
  | patch("tls_self_signed_cert"; "ca"; "front-proxy-ca"; {cert_pem: $front_proxy_crt, private_key_pem: $front_proxy_key})
  | patch("tls_private_key";      "ca"; "etcd-ca";        {private_key_pem: $etcd_key})
  | patch("tls_self_signed_cert"; "ca"; "etcd-ca";        {cert_pem: $etcd_crt, private_key_pem: $etcd_key})
  | patch("tls_private_key";      "sa"; null;             {private_key_pem: $sa_key, public_key_pem: $sa_pub})
  | .serial += 1
  ' v3-upgrade.tfstate > v3-upgrade-patched.tfstate

terraform state push v3-upgrade-patched.tfstate
```

Derived attributes of the swapped resources (fingerprints, validity
timestamps) still describe the throwaway values. That is fine: the module
only ever reads the PEMs, and `ignore_changes = all` means Terraform will
never reconcile these resources again.

## 6. Review the plan

```bash
terraform plan
```

Expected changes:

* **Destroyed:** the v2 provisioning shims — `null_resource.cluster_bootstrap`,
  `null_resource.control_plane_join[*]`, `null_resource.install_addons`,
  `random_id.certificate_key`, the `module.kubeconfig` and
  `module.join_config` shell-module internals, and `null_resource.node_join`
  in each worker pool. All of these are provisioner wrappers; destroying them
  touches nothing on the nodes.
* **Created:** their `terraform_data` replacements, the bootstrap token
  (`random_string.bootstrap_token_id`, `random_password.bootstrap_token_secret`,
  `terraform_data.bootstrap_token`), and the Terraform-signed admin credential
  (`tls_private_key.admin`, `tls_cert_request.admin`,
  `tls_locally_signed_cert.admin`).
* **Untouched:** every `hcloud_server`, load balancer, network and firewall,
  and the PKI resources you just seeded.

**Stop and investigate if the plan wants to replace or destroy any `hcloud_*`
resource, or touch the `tls_private_key.ca`/`tls_self_signed_cert.ca`/
`tls_private_key.sa` resources.**

## 7. Apply

```bash
terraform apply
```

What actually happens on the cluster:

* The PKI roots are rewritten on each control plane node with byte-identical
  content; the marker file makes every `kubeadm init`/`join` a no-op.
* A new bootstrap token Secret is created (v3 manages it declaratively).
* The addon manifests (Wigglenet, CCM, CSI) are re-applied; if v3 ships newer
  addon versions this rolls those components.
* A new admin kubeconfig is signed from the existing cluster CA. Previously
  distributed kubeconfigs keep working.

## 8. Verify and clean up

```bash
terraform output -raw kubeconfig > kubeconfig.new
kubectl --kubeconfig kubeconfig.new get nodes
```

Then:

* Delete the v2 long-lived bootstrap token: run `kubeadm token list` on a
  control plane node — the v2 token is the one expiring ~10 years after the
  cluster was created — and remove it with `kubeadm token delete <id>`.
  (The v3 token is the one whose id matches
  `terraform output -raw worker_join_config | grep token`.)
* Delete the local `pki/` directory and the plain-text state files
  (`v3-upgrade*.tfstate`) — both contain the cluster's root keys. Keep
  `v2-backup.tfstate` somewhere safe until you are confident.
* Optionally remove v2 leftovers on the nodes: `/root/cluster.yaml`,
  `/root/join-command.sh`, `/root/install-addons.sh`.
